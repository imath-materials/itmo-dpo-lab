Одна заявка как структура, а не длинная строка

n8n передаёт данные между узлами в виде элементов items. Типичный элемент содержит объект json с полями. Одна заявка может быть представлена так:

{
  "json": {
    "request_id": "DEMO-014",
    "topic": "Проектор для занятия",
    "room": "А-302",
    "priority": "high"
  }
}

Названия полей важны: room и audience — разные ключи. У следующего узла не получится прочесть поле, которого нет во входе.

Как работает выражение

Выражение подставляет значение из текущего элемента. Для входного JSON выше используйте:

{{ $json.topic }}

Ожидаемое значение — «Проектор для занятия». Вводить выражение нужно в поддерживающее expression поле интерфейса n8n, а не в обычный текстовый редактор.

Три распространённые ошибки

Опечатка

$json.topik не совпадает с topic.

Неправильный тип

Число 3 и строка "3" могут сравниваться по-разному.

Не тот элемент

После преобразования узел может получать другие поля или несколько items.

Проверяйте Output предыдущего узла, а затем сопоставляйте значение через панель данных. Не придумывайте поле по памяти.

Отработайте на учебном файле

  1. Откройте материал об узлах и данных.
  2. Найдите в JSON поля topic и priority.
  3. Настройте вывод темы в следующем узле через expression, а не копированием текста.
  4. Измените тему во входном узле и убедитесь, что результат обновился.

Проверьте себя

Что произойдёт, если заменить $json.topic на $json.room?

Выражение возьмёт поле room текущего item. Для нашего примера получится «А-302».

Почему нельзя сравнивать строку и число без проверки типа?

Операции сравнения и условия ожидают определённые типы значений; часть интерфейсов приводит их, часть — нет. Нужно проверить фактическое значение и тип во входных данных.
